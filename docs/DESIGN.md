# 设计取舍

这份文档解释「为什么这么组织」，改之前先读一遍，能省掉重复决策。

---

## 一、为什么拆成 preset + skills

**问题**：一开始所有内容都在 persona 里，写到最后 8,474 字符（约 4,200 tokens），每轮对话都固定占着。

拆开看，内容其实是两类：

| 类型 | 例子 | 特性 |
|---|---|---|
| **行为约束** | 称呼、五问铁律、探测栈、三轮交付 | 每次对话都要生效 |
| **技术知识** | Go 目录结构、JWT 方案、Worker 设计 | 特定任务才用得到 |

**行为约束不能搬进 skill** —— skill 是命中才加载的，没触发就等于不存在。你不能靠 skill 保证"每次回答第一句叫老大"。

所以：

```
preset (persona)  ← 行为层，恒定 4.7K 字符
skills/*          ← 知识层，按需加载，可无限扩展
```

**省下来的不只是 token**：你在做 PHP 项目时，不用背着 Go 和 Rust 的规则。

## 二、为什么 skill 不用 knowledge/ 目录

中间试过一版：把知识写成 `knowledge/01-stacks.md`、`02-backend.md`，让 agent 用 `read` 工具去读。

**问题**：

| 手搓 knowledge/ | 正式 skill |
|---|---|
| 没有 description | 有 description，模型能自己匹配 |
| 不能自动触发 | 命中场景自动加载 |
| 只属于某个 preset | 全局，其他模式也能用 |
| 不能被 catalog 索引 | 出现在技能列表里 |

`knowledge/*.md` 本质上是**手搓的 skill**。用正式机制后，三个问题一起解决。

## 三、为什么触发条件放在 bootstrap，不放在 persona

每加一个 skill 就往 persona 里加一行触发条件，persona 会重新膨胀：

```
3,271 → 3,585 → 3,910 → 4,332 → 4,452 → 4,577
```

涨的几乎全是路由列表。

**改法**：persona 只留一句「先加载 bootstrap，按其中路由表决定」，具体路由表放 `web-project-bootstrap` 的「零、技能路由表」。

结果：**persona 恒定，加 skill 只改 bootstrap。** 代价是每次多加载一次 bootstrap（约 12K 字符），但这个代价只在真正开工时支付一次。

## 四、为什么技能是「预制件」不是「参考资料」

**参考资料**：

> 建议使用统一的响应体。

**预制件**：

> 响应体必须是 `{code,msg,data}`。错误码分五段。5xx 的 msg 一律是「服务器繁忙」。违反即打回重写。

差别在于**能不能直接执行**。LLM 是模式匹配机器，给它"建议"它会自由发挥，给它"判据 + 数字"它才能照着做。

所以每个技能里都有三样东西：

1. **决策树**（什么情况选什么）
2. **数字**（200 行、40–60%、44px、8KB、15 分钟）
3. **验收清单**（过不了算没做完）

## 五、为什么强调机制而不是规范

写「请使用 Ant Design 组件」—— 没用。它照样 `<button>`。

真正有效的是三层机制：

```
① 单一出口        @/components/index.ts
② eslint 拦截     no-restricted-imports / no-restricted-syntax
③ 让正确用法更短  await confirm('...') 比 Modal.confirm({8 个参数}) 短一半
```

**第 ③ 条最容易被忽略**：如果封装版比原生写法长，agent 一定选原生的，lint 也拦不住它绕过。

## 六、persona 的优先级设计

persona 里内容是**有序**的，前面优先级更高：

```
称呼与风格          ← 每次生效
任务启动协议        ← 每次开工
技能路由            ← 每次开工
铁律一：探测栈      ← 每次开工
铁律二：五问        ← 每次开发任务
布局沟通规则        ← 涉及 UI 时
分层交付            ← 大页面时
架构默认            ← 建议架构时
工程习惯            ← 写代码时
```

越靠前越不能违反。五问铁律排在第三，就是为了压过"赶紧开始写"的冲动。

## 七、已知取舍

| 取舍 | 代价 | 为什么接受 |
|---|---|---|
| 两级路由（persona → bootstrap → skill） | 多加载一次 12K | 换 persona 恒定 |
| 五问铁律会拖慢小任务 | 每任务多几轮对话 | 用"琐碎改动例外"缓解 |
| 12 个技能有内容重叠 | 偶尔重复加载 | 各技能自包含，避免交叉引用导致漏读 |
| 中文为主 | 国际用户门槛 | 目标用户是中文开发者，术语保留英文 |
| 不绑定 DSH 版本 | 插件 API 变化可能要改 | 只用了稳定的插件 id |

---

## 八、不要做的事

- **不要把知识搬回 persona**，会重新膨胀
- **不要给 skill 加交叉引用链**（A 说"见 B"，B 说"见 C"），模型会漏读；宁可重复写一遍
- **不要为了提高覆盖率/行数加规则**，每条规则都该来自一个真实踩过的坑
- **不要在没有验收标准的情况下加技能**，否则它会变成"建议"
